# 06. 구현 백로그와 인수 기준

## 이번 산출물의 범위

design 문서·설정 예시만 생성했다. 실제 키 조회·인증 테스트·API 수집·HF 생성/업로드·GitHub 변경·런타임 설치·자동화 등록은 다음 구현 작업이다. 이번 문서의 검증은 링크·JSON 문법·파일 무결성을 대상으로 하며 시스템 동작 검증이 아니다.

## 단계별 작업

| 단계 | 구현 작업 | 인수 기준 |
|---|---|---|
| P0-1 기반 | HF namespace 확인, 키 loader, 레포 HEAD·lock 점검, 서비스 registry | 비밀 없는 진단, 환경변수/파일 우선순위와 불일치 처리 확인 |
| P0-2 최소 수집 | 아파트 일반 매매·전월세 한 지역·한 월 | 페이지·단위·정상 0건·오류 구별, 원문 관측 결속 |
| P0-3 로컬 데이터 | Parquet·DuckDB 필터, SQLite 실행 상태 | 재실행 시 중복/복구 정책, 같은 snapshot에 같은 결과 |
| P0-4 HF | private 후보 commit, 고정 다운로드, manifest 활성화 | 허용 파일만 업로드, SHA·행 수 대조, 이전 릴리스 rollback |
| P1-1 도구 | 데이터 조회 MCP, 기존 MCP와 Context 연결 | 임의 URL/SQL 금지, provenance·coverage 전달 |
| P1-2 물건 | 토지 거래·건축물·주소/필지 식별 | 마스킹과 후보 매칭 보존, 일반/상세 중복 관리 |
| P1-3 규제 | 필지 지정→행위제한→법령·조례·고시 | 현재/과거 구별, 미확정 시 유보 |
| P2-1 업무 | 사례 선택·계산·matter bundle·상태 머신 | 입력부터 초안까지 근거·수치 재현 |
| P2-2 지식 | Claim 제안·관계 schema·개정 영향·Wiki PR | 기존 ID·검토 계약·고정 판본 유지 |
| P3 확장 | 기타 거래유형·평가셋·선택적 의미 검색 | baseline 대비 품질 비교, 비용·호출량 실측 |

HF namespace와 토큰 권한은 실제 업로드 단계의 필수 정보다. 답이 없으면 로컬 수집·조회까지 진행 가능하지만 임의 namespace를 생성하거나 public fallback하지 않는다. 데이터별 이용 조건이 미확정이면 해당 자료의 외부 업로드는 보류하고 허용된 로컬 범위부터 구현한다.

## 검증 전략

| 층 | 핵심 사례 |
|---|---|
| credential | BOM·개행·다중 값·빈 env·인코딩 키, 값·URL·예외의 비밀 가림 |
| API | HTTP 200 오류 XML, 정상 0건, timeout, 429, 반복/누락 페이지, total 변경, schema drift |
| 단위·정규화 | 만원→원, 보증금/월세 분리, null≠0, 면적 종류, 날짜·지역코드 |
| 동일성 | 같은 조건의 별개 거래, 일반/상세 중복, 마스킹 주소, 불확실 정정/취소 |
| HF 릴리스 | 잘못된 namespace·public 대상·권한 부족·중간 업로드·해시 실패·rollback |
| 근거 | 원문/요약 구분, 다른 판본, FAQ/정식 해석 구별, 반대 근거, unresolved dependency |
| 계산 | Decimal·반올림·보정치 근거·결측, 독립적으로 확인한 기대값 |
| 업무 | 사건별 격리·상태 전이 guard·재개·오래된 관측·확정 유보 |

fixture는 합성 또는 비밀 제거된 허용 응답으로 만든다. 실제 키 없는 CI에서 재현해야 한다. 실제 연결 점검은 별도 bounded smoke로 수행하며 전수 법적 검증이라고 보고하지 않는다.

처음에는 검토된 소규모 실무 사례 20건 안팎을 목표로 한다. 숫자는 제안이며 현재 보유 평가셋 규모가 아니다. 아파트·토지·임대차·보상과 유보 사례를 포함한다. 근거 정밀도·필수 쟁점 누락·판본 적합성·계산 오차·유보 판단·조회 비용/시간을 측정한다. 배포 임계치는 baseline과 검토 결과로 정하며 근거 없이 수치를 확정하지 않는다.

시험셋은 회차·주제별 분리, 정답·해설 검색 차단, 유사문항 누수 점검이 필요하다. 1차 최종 정답과 2차 자체 해설의 권위를 구별한다. 사람 검토와 에이전트 검토를 보고서에 별도 표시한다.

## 운영과 복구

- SQLite는 단일 writer를 기본으로 하고 작업 lock·idempotency key·중단 상태를 기록한다.
- idempotency는 query 조건·서비스·파서·snapshot scope에 결속한다. 재관측 자체를 삭제하는 중복 제거로 사용하지 않는다.
- 로그는 run_id·서비스·건수·시간·가려진 오류만 남긴다. 전체 환경·요청 URL·토큰·응답 무검사 출력은 금지한다.
- 오래된 캐시 fallback은 사용 여부·시각·사유를 표시한다. 최신 조회 성공으로 표시하지 않는다.
- API outage·HF outage에는 부분 결과/이전 snapshot과 미확인 범위를 명시한다.
- snapshot과 SQLite 백업을 함께 검증하고 복원 시 manifest·파일 해시를 대조한다.
- 보존 기간·HF 용량·호출 예산·갱신 주기는 실제 사용량과 제공기관 조건을 확인한 뒤 설정한다.

5. 최소 지역·월 smoke → 로컬 조회 → HF 후보 → manifest 검증 순서로 연결한다.
